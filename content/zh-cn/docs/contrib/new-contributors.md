本页面提供了一些较为通用的建议，介绍你可以通过哪些方式为 SpinKube 做出贡献，以及如何着手去做。

如果你需要一份关于代码贡献具体细节的参考，请参阅[编写代码]({{< ref "writing-code" >}})文档。

## 起步步骤

按照以下步骤开始，你就能顺利地成为 SpinKube 的贡献者。

### 加入交流

可以说，协作与沟通是开源开发中最重要的环节。就项目方向达成共识，并确保你的工作与该方向保持一致，是让你的工作被接受的关键。因此，尽早且经常地加入交流十分重要。

要加入交流，请访问 [CNCF Slack](https://cloud-native.slack.com/archives/C06PC7JA1EE) 上的 `#spinkube` 频道。

### 阅读文档

SpinKube 文档是一个很好的起点。它包含如何开始使用项目、如何做贡献以及如何使用项目的信息，也是了解项目架构与设计的绝佳去处。

SpinKube 的文档很棒，但并非完美无缺。如果你发现内容不清晰或有错误，请提交 pull request 予以修正。更多信息请参阅[编写文档]({{< ref "writing-documentation" >}})指南。

### 分拣 issue

如果某个 issue 报告了 bug，请尝试复现它。如果能够复现且看起来有效，请在 issue 中注明你已确认该 bug，并确保 issue 的标签设置得当。如果无法复现，请向报告者询问更多信息。

### 编写测试

可以考虑为 bug 的行为编写一个测试，即使你并不亲自修复这个 bug。

带有 `good first issue` 标签的 issue 是很好的起点。这些 issue 被特别标记为适合新贡献者上手的工作。

## 一些准则

作为大型项目的新人，很容易感到挫败。以下建议可以让你的 SpinKube 贡献工作更有价值、更有收获。

### 选择一个你在意的、熟悉的，或者想学习的领域

你不必在动手之前就成为某个领域的专家；正是通过持续不断地向代码贡献，你才会成为专家。

### 从小事做起

小 issue 比大 issue 更容易获得反馈，对新贡献者来说尤其如此；维护者更有可能抽出时间来评审一个小的改动。

### 如果要承担一个大任务，请先确保你的想法获得支持

也就是说，在修复 issue 之前，先请他人确认 bug 确实存在；在动手实现一个新功能之前，先确保大家对提案已达成共识。

### 大胆一点！留下反馈！

把你的观点公之于众，说“这个 issue 是有效的”或“这个 patch 还需要改进”，有时可能让人忐忑，但这是项目前进的唯一方式。整个 SpinKube 社区的贡献最终会产生远超任何个人的影响力。没有你，我们做不到！

### 标记“可供评审”时，宁可谨慎一些

如果你实在不确定某个 pull request 是否已可供评审，就不要做此标记。可以留下评论，说明你的想法。如果你大体确定但不是完全确定，也可以在 [Slack](https://cloud-native.slack.com/archives/C06PC7JA1EE) 上问问，看看是否有人能证实你的判断。

### 等待反馈，并回应收到的反馈

专注于一个或两个 issue，从头到尾跟进完成，然后再开始下一轮。那种同时接下大量 issue、任由其中一些不了了之的“霰弹枪式”做法，最终往往弊大于利。

### 严谨对待

当我们说“这个 pull request 必须包含文档和测试”时，是认真的。如果一个 patch 缺少文档和测试，最好有一个充分的理由。诸如“我找不到这个功能的现有测试”之类的说辞并没有多少说服力；即便这是事实，那也意味着你承担着为该功能编写第一批测试的格外重要的任务，而不是可以免写测试。

### 保持耐心

你的 issue 或 patch 不总是能很快得到评审。这并非针对个人，因为需要处理的 issue 和 pull request 实在太多了。

让你的 patch 保持更新很重要。请在 GitHub 上查看你的 pull request，确保所有评审意见都已得到处理。
